## 🔍 詳細分析

### 実世界データでの失敗パターン

#### 1. Web App カテゴリ (0/22 = 0%)

**失敗例**:
```
Expected: web_app
Command: "リアルタイムメッセージング機能を持つチームコラボレーションプラットフォームを構築してください..."
Predicted: machine_learning (誤り)
```

**原因分析**:
- 「プラットフォーム」「構築」などの汎用的な言葉が machine_learning と強く関連
- 実世界の製品名（Slack, Notion, Figma等）が訓練データに含まれていない
- 短文での特徴抽出が不十分

#### 2. API カテゴリ (2/7 = 28.6%)

**成功例**:
- Twilio (通信API) → api ✅
- Postman (API開発ツール) → api ✅

**失敗例**:
- Stripe (決済API) → network ❌
- Google Maps (地図API) → network ❌
- SendGrid (メールAPI) → network ❌
- AWS (クラウドAPI) → general ❌
- OpenAI (LLM API) → machine_learning ❌

**原因**: 「API」という単語だけでは不十分で、実際のAPIサービスの文脈理解が必要

#### 3. Visualization カテゴリ (0/4 = 0%)

すべて machine_learning と誤分類:
- Figma (デザインツール)
- Tableau (BIツール)
- Grafana (監視ダッシュボード)
- Canva (グラフィックデザイン)

**原因**: 「分析」「ダッシュボード」などの用語が machine_learning と強く関連

### 訓練データの問題点

#### 1. テンプレートベースの限界

**訓練データ例**:
```
"TensorFlow でCNN モデルを訓練"
"React でWeb アプリ作成"
"Pandas でデータ分析"
```

**実世界データ例**:
```
"リアルタイムメッセージング機能を持つチームコラボレーションプラットフォームを構築してください。
チャンネル作成、ダイレクトメッセージ、ファイル共有、スレッド機能、リアクション、通知システム、
検索機能、ユーザーステータス管理を含めてください。"
```

**ギャップ**:
- 訓練データ: 技術キーワード中心、短文
- 実世界データ: 機能要件記述、専門用語、長文

#### 2. カテゴリ境界の曖昧性

**混同しやすい組み合わせ**:
1. **machine_learning ↔ data_analysis**: 「分析」「モデル」などの共通用語
2. **web_app ↔ api**: 多くのWeb アプリが API を含む
3. **api ↔ network**: 通信関連 API の分類が曖昧
4. **visualization ↔ data_analysis**: データ可視化は両方に関連

# 再導入する特徴
